# Phase 4: dual-write observability and reconciliation

Design specification for observing a **future** legacy + HTTPS dual-write. Decision record:
[`decisions/0005-phase4-dual-write-observability.md`](decisions/0005-phase4-dual-write-observability.md).
Transport decision: [`decisions/0004-phase4-https-batch-ingest-adapter.md`](decisions/0004-phase4-https-batch-ingest-adapter.md)
and [`phase4-https-batch-ingest.md`](phase4-https-batch-ingest.md), whose §12 defines the
ingest counters this document reads and whose §13 names this work.

Source of truth: `hear/ingest/reconcile.py`. Staged artifacts:
`phase4-dual-write-reconciliation/` (schema, 18 fixtures, manifest), generated by
`tools/gen_reconcile_contracts.py` and gated in CI.

> **Status.** Design and contracts only. Dual-write is **not** enabled by this document, no
> comparator is scheduled, no service is created, no fleet or cluster object is touched, and
> no telemetry credential is issued. The legacy path stays authoritative throughout Phase 4
> and is not modified.

## 1. Scope

**In scope:** correlation identity and credential binding; the mismatch/audit receipt; what
"the same" means for each compared field; timing and order tolerances; payload, hash and
redaction constraints; the duplicate/loss/stale/error classification; metrics, SLOs and
alerts; sampling and cost controls; the repair-queue boundary; operator evidence; fault
injection cases; freeze/codegen compatibility; rollback criteria.

**Explicitly not in scope:** enabling dual-write; writing the comparator; any cluster,
CronJob, dashboard object or alert rule; any new credential, service account or telemetry
token; changing a legacy writer or reader; a production reconciliation service; retention
approval (a data-governance decision, §13).

## 2. Position

| Party | Role in Phase 4 |
|---|---|
| `tools/hear_heartbeat_receiver.py`, `tools/hear_mqtt_bridge.py`, `tools/hear_drain.py` → `hear/pool.py` | **Authoritative.** Unchanged. Every operator default still reads these. |
| HTTPS batch ingest (`docs/phase4-https-batch-ingest.md`) | **Claimant.** Additive, off by default, enabled one source at a time. |
| The comparator | **Auditor.** Reads both, writes receipts, changes neither. |

The auditor has no write path into either subject. Everything below follows from that.

## 3. Correlation identity

### 3.1 The two identity schemes, and why neither is converted

| Side | Identity | Derivation |
|---|---|---|
| Legacy | `record_uid` | `sha256("v2" ⋮ telemetry_path ⋮ device_id ⋮ idempotency_key)`, or `sha256(canonical body)` when the node minted no key (`tools/hear_heartbeat_receiver.py`) |
| Canonical | `event_id` | UUIDv5 over ADR 0001's closed identity tuple (`hear/ingest/envelope.py`) |

Neither is computable from the other, and neither may move: the first is live on six nodes,
the second is frozen for the life of the v1 major. **The comparator therefore converts
nothing.** The dual-writer records the `(legacy_uid, event_id)` pair in the same transaction
as the canonical write; the comparator joins on that recorded pair.

Re-deriving would be worse than impossible — it would be *plausible*. A comparator that
recomputes `event_id` from a legacy row is reimplementing the code it audits, and a bug
shared by both implementations makes the two sides agree about the wrong thing.

### 3.2 The join key

```
correlation_id = "<side>:" + sha256(contract ⋮ side ⋮ site_id ⋮ device_id ⋮ telemetry_path ⋮ anchor)
```

- `side` is `legacy` whenever a legacy row exists, otherwise `canonical`. Legacy is
  authoritative, and an authoritative record must not change identity when the claimant
  appears or disappears.
- The side prefix keeps the two identity namespaces from colliding: a `record_uid` and an
  `event_id` that happened to be the same string are still different keys.
- `site_id`, `device_id` and `telemetry_path` are identity inputs, mirroring the scoping the
  legacy receiver already applies for exactly the reason it applies it — one device's key
  must not shadow another's.

### 3.3 Binding

| `binding` | Meaning | Consequence |
|---|---|---|
| `bound` | the dual-writer recorded both identities | normal comparison |
| `legacy_orphan` | authoritative row with no canonical identity | candidate `missing_canonical` after grace |
| `canonical_orphan` | canonical row the dual-writer did not produce | `missing_legacy`, warn |

A pair with neither identity is not a pair; constructing one raises rather than inventing a
key.

### 3.4 Credential binding

Each side records the **enrolled** `principal_id`, the credential `scope`
(`device`/`site`/`unknown`) and an opaque `key_id` rotation label. The receipt carries those
three fields and a `matched` boolean, and nothing else about authentication.

- `matched` requires a non-null principal on both sides *and* equal scope. Two sides that
  both recorded no principal have not agreed on anything; `None == None` must not read as
  agreement.
- An unrecognised scope degrades to `unknown` and cannot match.
- A disagreement is `identity_divergence` at critical severity, judged **before every other
  check**. A pair that is not about the same producer is not a pair, and every later
  comparison over it would be meaningless. This is the reconciliation-side counterpart to
  the batch path's per-item credential binding, which refuses an item whose `device_id`
  contradicts its credential.
- The comparator introduces **no credential of its own** and authenticates as nothing. There
  is no field in the receipt that a token, header value or key body could occupy.

## 4. What "the same" means

Comparison is by stable identity and source partition, never by arrival order. The compared
state is an **explicit projection**, not a whole stored row: hashing a whole row makes every
additive field a mismatch, and that is the reconciler people switch off in week two.

| Comparator | Applied to | Tolerance |
|---|---|---|
| `hash` | retained raw objects | SHA-256 equal. A tolerance on retained bytes is a tolerance on corruption. |
| `exact` | identity strings, GPS-anchored instants | equal |
| `tier` | unanchored instants | clock tier equal, **value ignored** |
| `count` | counters, row counts | equal; conservation closes per source/day/node |
| `numeric` | solver and model outputs | `abs diff ≤ declared tolerance` **and** model-card identity equal |

`state_hash` is `sha256` over the canonical JSON of the projection — sorted keys, no
whitespace, no NaN/Infinity, ASCII-escaped — so two comparators in different processes
produce the same digest for the same projection.

**Unanchored time is compared as a tier, never as a value.** Two honest writers with no GPS
fix will disagree on a wall-clock instant. Reporting that as a mismatch manufactures a
permanent red signal out of correct behaviour.

## 5. Timing and order tolerances

| Bound | Value | Why |
|---|---|---|
| `LIVE_GRACE_S` | 300 s | A canonical write that has not landed yet is `pending`, not lost. Without this the reconciler pages on its own scheduling jitter, gets muted, and the one real loss arrives muted. |
| `BACKFILL_GRACE_S` | 86 400 s | `hear_drain.py` replays an SD backlog in bulk; a day-late canonical row on an import path is normal. Judging backfill on the live window would page on every drain run. |
| `ORDER_GRACE_S` | 300 s | Batches legitimately arrive out of order and the server never reorders. Only a `batch_sequence` gap inside one `boot_id` that outlives this window is evidence. |

Ordering is producer-local. A changed `boot_id` makes sequences incomparable — the same rule
`hear_drain.py` already applies when it treats a changed boot ID as a cursor discontinuity
rather than a continuation. There is no global sequence and the comparator must not invent
one.

## 6. Classification

Fifteen members, closed. Every compared pair reaches exactly one, or stays `pending`.

| Classification | Severity | Repair | Meaning |
|---|---|---|---|
| `match` | info | none | both sides wrote the same projection |
| `pending` | info | none | canonical has not landed and the grace window is open — **no receipt is written** |
| `missing_canonical` | **critical** | `replay_inbox` | the loss this exercise exists to find |
| `missing_legacy` | warn | manual | a canonical row the authoritative path never wrote |
| `duplicate_canonical` | **critical** | manual | identity-based dedup failed |
| `duplicate_legacy` | warn | manual | pre-existing legacy redelivery; canonical collapsing it is the designed outcome |
| `stale_canonical` | warn | `replay_outbox` | present, but mirrors an older revision |
| `stale_legacy` | warn | manual | the authoritative row is the older one (import paths) |
| `outcome_divergence` | **critical** | manual | one side stored, the other durably refused |
| `value_divergence` | **critical** | manual | a compared field is outside tolerance |
| `order_divergence` | warn | none | a producer sequence gap outlived the order window |
| `identity_divergence` | **critical** | manual | the two sides disagree about the authenticated producer |
| `error_legacy` | **critical** | manual | the authoritative write reported failure — already data loss |
| `error_canonical` | warn | `replay_inbox` | the claimant failed; legacy stands |
| `unclassified` | **critical** | manual | no verdict was derivable |

**Order of judgement is load-bearing:** identity → errors → duplication → absence → outcome
→ order → values → staleness → hashes.

- Identity first: a mismatched producer makes every later comparison meaningless.
- Errors before absence: "the write failed and we know it" is evidence; "nothing is there"
  is only the absence of evidence.
- Duplication before divergence: with two canonical rows, "which value differs" has no
  answer.

**Severity reasoning worth stating.** `duplicate_legacy` is warn because MQTT QoS 1
redelivery is pre-existing legacy behaviour — blaming the new path for the old one's shape
trains an operator to ignore the counter. `error_legacy` is critical even though dual-write
did not cause it, because it is the one failure that is *already* data loss. `unclassified`
is critical because undecidable is louder than wrong: a comparator that cannot classify has
stopped being evidence.

**Unknown is not `match`.** A member this build does not recognise is preserved verbatim,
counted as `unclassified` so the accounting still closes, and marked `actionable: false` so
no automated step touches it — the reconciliation analogue of ADR 0001's non-dispatchable
rule.

### 6.1 Conservation

```
compared == pending + match + Σ(mismatch classifications)
```

`reconcile.conservation()` asserts it. If it does not close, the run is not evidence and
must not be reported as one — the same discipline the batch path applies to
`submitted = accepted + duplicate + refused + deferred`.

## 7. The receipt

`hear.reconcile.receipt.v1` — schema and 18 worked fixtures in
`phase4-dual-write-reconciliation/`. One receipt per terminal finding.

| Block | Carries |
|---|---|
| `receipt_id` | `uuid5(namespace, contract ⋮ run_id ⋮ correlation_id)` — deterministic, so a re-run after a comparator crash converges instead of duplicating |
| `run_id`, `window`, `emitted_at` | which run and which window produced it |
| `correlation` | key, binding, both identities, site/device/path/source |
| `credential` | enrolled principal, scope and opaque `key_id` per side, plus `matched` |
| `sides.legacy` / `sides.canonical` | outcome, row count, `state_hash`, written/observed instants, clock tier, writer and build, reason codes |
| `verdict` | classification, severity, repair action, `actionable`, notes |
| `differences` | field path, both redacted values, comparator, tolerance, `quoted` flag |
| `differences_dropped` | how many were elided by the cap — the loss is recorded, never silent |
| `disposition` | `repairable`, `repair_action`, `queued` (always `false`), `queue_ref` |
| `sampling` | `sampled`, `rate_denominator`, `forced_reason` |
| `evidence` | redaction profile and the object keys of the retained raw bytes on each side |
| `comparator` | comparator name, build and receipt major — so a bad comparator release is attributable |

A `pending` comparison **cannot** produce a receipt: building one raises. `pending` is a
scheduling state, not a finding, and writing it down fills the store with rows meaning "ask
again".

The receipt is an index into evidence, never the evidence: ≤ 32 differences, ≤ 8 KiB
encoded. An oversized receipt is refused rather than truncated, because a silently truncated
audit record is worse than a missing one.

### 7.1 Payload, hash and redaction constraints

Redaction is **deny-list-first over an allow list**:

1. If the field path matches the deny pattern — `lat`, `lon`, `lng`, `latitude`,
   `longitude`, `coord*`, `position`, `token`, `secret`, `password`, `credential`, `bearer`,
   `auth*`, `private`, `pem`, `payload`, `body`, `raw`, `audio`, `pcm`, `samples`,
   `clip_bytes` — it is redacted. Always. `tools/coord_guard.py` already makes a real-world
   coordinate in the tree merge-blocking; a receipt store is the obvious way to reintroduce
   one, so location-shaped paths are unquotable by construction rather than by reviewer
   attention.
2. Otherwise, if the path is on the explicit allow list *and* the value is a scalar, it is
   quoted literally.
3. Otherwise it is redacted.

A redacted value is `{"redacted": "sha256:<16 hex>"}` — stable, comparable, non-invertible.
`key_id` is deliberately **not** denied: an opaque rotation label is how a credential change
is attributed, and redacting it would make rotation unauditable.

An unknown path defaults to redacted. An allow list defaults to hidden; a deny list defaults
to leaked, and the next field added upstream is exactly the case that decides which.

Raw bytes never enter a receipt. They stay where the ingest path already retains them and
the receipt carries only the object key.

## 8. Metrics, SLOs and alerts

### 8.1 Metrics

Labels: `site`, `device_id`, `source`, `class`, `severity`, `side`. Never a token, never a
payload, never a coordinate.

| Metric | Type | Use |
|---|---|---|
| `reconcile_pairs_compared_total` | counter | denominator for every rate below |
| `reconcile_classified_total{class,severity}` | counter | the conservation equation, live |
| `reconcile_pending` | gauge | pairs inside the grace window; a rising floor means the canonical path is falling behind, not that it lost anything |
| `reconcile_unclassified_total` | counter | comparator competence; target is exactly zero |
| `reconcile_binding_missing_total{side}` | counter | dual-writer failed to record a pair |
| `reconcile_lag_seconds` | histogram | canonical `written_at` − legacy `written_at` |
| `reconcile_window_closed_timestamp` | gauge | freshness; alert on its **age**, not its value |
| `reconcile_run_duration_seconds` | histogram | cost control input |
| `reconcile_receipts_written_total{class}` | counter | store growth, and the audit trail's own volume |
| `reconcile_coverage_ratio` | gauge | compared pairs ÷ legacy rows in the window |
| `reconcile_audit_denominator` | gauge | the sampling rate actually in force |
| `reconcile_repair_queue_depth{class}` | gauge | advisory work list; **not** an automation input |

These are computed from receipts and run manifests. They do not replace the ingest counters
in `phase4-https-batch-ingest.md` §12; `ingest_dual_write_mismatch_total{class}` there is the
same signal as `reconcile_classified_total` restricted to mismatch classes, and the two must
agree.

### 8.2 SLOs

| SLO | Target | Source |
|---|---|---|
| Unexplained mismatch | **0** over a rolling 7 days | the Phase 4 exit gate, §13.3 of the ingest spec |
| Unclassified | **0** per run | `reconcile_unclassified_total` |
| Coverage | ≥ 99.9 % of legacy rows in the window | `reconcile_coverage_ratio` |
| Freshness | window closed < 15 min ago | age of `reconcile_window_closed_timestamp` |
| Conservation | closes on every run | run manifest |
| Comparator cost | ≤ 1 vCPU-minute per 10 000 pairs | `reconcile_run_duration_seconds` |

"Unexplained" is doing real work: `duplicate_legacy`, `order_divergence`, `stale_legacy` on
an import path and `pending` are **expected** classes with recorded reasons and do not
consume the budget. Anything else does.

The p99 ingest-lag SLO is still an open operator decision (ingest spec §16.1). The freshness
SLO here is stated independently of it so this document does not silently pick a number that
belongs to an operator.

### 8.3 Alerts

| Alert | Condition | Severity |
|---|---|---|
| Identity divergence | `identity_divergence` > 0 | page |
| Canonical loss | `missing_canonical` > 0 sustained 2 runs | page |
| Comparator incompetent | `unclassified` > 0 | page |
| Comparator stalled | `reconcile_window_closed_timestamp` older than 1 h | page |
| **Implausible zero** | `pairs_compared == 0` while ingest counters advanced | page |
| Conservation broken | run manifest does not close | page |
| Duplicate canonical | `duplicate_canonical` > 0 | ticket |
| Divergence drift | `value_divergence` or `outcome_divergence` rate rising over 24 h | ticket |
| Receipt store growth | receipts/run above the cost ceiling | ticket |

Two rules constrain this list:

- **Alert on implausible zeros, not only on spikes.** A comparator that silently stopped
  produces a perfect dashboard. This is the same instinct the ingest spec applies to
  `ingest_refusals_total`.
- **No alert here may fire on legacy health.** Legacy is authoritative and unchanged; a new
  page against an unchanged path is a failure mode introduced by the act of observing it.
  Legacy defects surface as `error_legacy` receipts, which route to the existing owner of
  that path.

## 9. Sampling and cost control

| Rule | Value |
|---|---|
| Mismatch receipts | **always written**, never sampled |
| Match (audit) receipts | 1-in-N, default N = 1000, deterministic on `correlation_id` |
| Forced full capture | first hour after enabling a source; first full day per board class (`esp32s3-i2s-gps`, `xiao-s3-pps`); any window containing a fault-injection drill; any window where a mismatch fired |
| Receipt cap | ≤ 32 differences, ≤ 8 KiB encoded |
| Cost ceiling | ≤ 1 vCPU-minute per 10 000 pairs, on existing hardware |

Sampling a failure signal makes the reconciler a coin flip, so cost is controlled on the
match side only. Determinism matters twice: a re-run of a window produces the same audit
set, and coverage is therefore computable rather than assumed.

A misconfigured denominator (0 or negative) samples **everything**. Failing open costs
storage; failing closed costs the evidence the comparator exists to produce.

If the cost ceiling is breached, the order of response is: raise the audit denominator →
narrow the window → reduce forced captures. Never reduce mismatch capture.

## 10. Repair queue boundary

The comparator is an auditor. It has no write path into either subject.

**Permitted:** `none`, `replay_inbox`, `replay_outbox`, `manual_review`. Replay is the
existing durable inbox/outbox replay, which is already idempotent because identity — not
arrival order — deduplicates.

**Forbidden, and not to be added quietly later:** editing a canonical row; editing a legacy
row; deleting a duplicate; re-deriving an `event_id` or a `record_uid`; back-filling a
missing row from the other side; auto-enqueueing any of the above.

Every emitted receipt has `disposition.queued = false`. The repair queue is an **advisory
work list** built by an operator from receipts; a human dequeues, and the replay that
results is an ordinary operation of the existing store, attributable to that human. An
auditor with write access to its subject is not an auditor.

## 11. Operator evidence

One page, and every panel resolves to a receipt query rather than to a number with no
provenance:

1. **Conservation** — compared vs. the sum of classes, per run. Red if it does not close.
2. **Class breakdown** — stacked by severity over 7 days, with the exit gate's zero line.
3. **Freshness and coverage** — window-closed age and coverage ratio.
4. **Lag distribution** — `reconcile_lag_seconds` p50/p95/p99 per source.
5. **Top correlations** — the newest critical receipts with their `receipt_id`, so the
   dashboard is an index into evidence rather than a summary of it.
6. **Repair work list** — queue depth per class, explicitly labelled advisory.

**Evidence bundle** for a gate review, produced per run: the run manifest (window, counts,
conservation result, comparator build), the class breakdown, the `receipt_id` list for every
critical finding, and the sampling parameters in force. The bundle is reproducible — the
same window re-run produces the same receipt ids — which is what makes "seven days with zero
unexplained differences" a claim somebody else can check.

## 12. Fault injection

Each case is a fixture in `phase4-dual-write-reconciliation/fixtures/` and a test in
`tests/test_reconcile_receipt_v1.py`. The fixture set covers every classification; a
vocabulary member with no worked example is a claim nobody checked.

| # | Injected fault | Expected |
|---|---|---|
| 1 | Nothing; both sides write the same projection | `match`, forced into the audit sample |
| 2 | Canonical write delayed 30 s | `pending`, no receipt |
| 3 | Canonical write never happens | `missing_canonical`, critical, `replay_inbox` |
| 4 | Drain backlog replayed 6 h later | `pending` on the backfill window |
| 5 | Canonical dedup fails; two rows | `duplicate_canonical`, judged before any value check |
| 6 | Counter drifts by one row | `value_divergence`, critical |
| 7 | Credential forged onto another node's `device_id` | `identity_divergence`, judged first |
| 8 | No GPS fix on either side | `match` — tier compared, values ignored |
| 9 | Legacy accepts, canonical durably refuses | `outcome_divergence` |
| 10 | Canonical row with no legacy counterpart | `missing_legacy`, `canonical_orphan` |
| 11 | `batch_sequence` gap persisting past the order window | `order_divergence`, warn |
| 12 | One side publishes no `state_hash` | `unclassified`, critical |
| 13 | A coordinate and a bearer credential differ | `value_divergence` with both values redacted |
| 14 | Canonical durable write errors | `error_canonical`, warn, `replay_inbox` |
| 15 | Legacy durable write errors | `error_legacy`, critical |
| 16 | MQTT QoS 1 redelivery produces two legacy rows | `duplicate_legacy`, warn |
| 17 | Canonical mirrors an older legacy revision | `stale_canonical`, `replay_outbox` |
| 18 | Import writes canonical from a newer revision | `stale_legacy`, manual review |

Cases 2/4, 8, 11 and 16 exist specifically to prove the comparator does **not** fire on
correct behaviour. A reconciler's false-positive rate is what decides whether anyone reads
it, and those four are the false positives this design would otherwise have.

Drills that belong to the ingest lane and are read here rather than duplicated: node outage
and reconnect, replayed batch, Redis loss, read-only PVC, and the MQTT bridge's
drop-before-durability defect (issue #104).

## 13. Freeze and codegen compatibility

- `hear/ingest/reconcile.py` is the source of truth; every artifact is generated by
  `tools/gen_reconcile_contracts.py`, wired into the CI job `generated headers are current`.
  A staged artifact with no drift gate stops describing its source just as silently as a
  published one would.
- The artifacts are staged under `phase4-dual-write-reconciliation/` rather than
  `contracts/`, because publishing a contract id regenerates the hashed Phase 0 freeze
  baseline that the in-flight ingest lane is already regenerating. The manifest records
  `status: staged` with the reason; ADR 0005 states the five-step promotion, which is a move
  plus a regeneration and **no content change**.
- The contract id constant is named `RECEIPT_CONTRACT_ID`, not `RECEIPT_SCHEMA_ID`, because
  `tools/freeze_contracts.py` harvests `[A-Z_]*SCHEMA[A-Z_]*` assignments as published
  contract ids — the same trap that tool and `tools/check_contract_layout.py` already
  document about their own constants. A test asserts the constant stays unharvestable, so
  the reason cannot be lost to a rename.
- **This PR moves no baseline hash.** `tools/freeze_contracts.py --check`,
  `tools/check_contract_layout.py`, `tools/recoupling_guard.py` and `tools/coord_guard.py`
  all pass unchanged.
- Within the major, everything is additive: `additionalProperties: true` at every level, an
  unknown classification member is preserved and held back from automated action, and a
  receipt from a newer major is refused with a reason rather than guessed.
- A new major is a new file, never an edit to this one.

**Open, and deliberately not decided here:** mismatch-receipt retention. `missing_canonical`
and `identity_divergence` receipts are the evidence for a gate review and for an
authentication incident respectively, so their retention is a
`docs/data-governance.md` approval, not a design choice. The design bounds *size* and
*volume*; it does not set a destruction schedule.

## 14. Rollback

Rollback is layered, and each layer is cheaper than the one under it.

| Layer | Trigger | Action |
|---|---|---|
| Comparator | cost ceiling breached; `unclassified` > 0 on two consecutive runs; receipt store growth beyond budget | stop scheduling the comparator. Receipts stop; both writers are unaffected; no data is deleted. |
| Comparator release | a comparator build changes verdicts with no change on either side | roll the comparator back and **re-run the window** — deterministic receipt ids make the two runs directly comparable |
| Dual-write | the triggers in `phase4-https-batch-ingest.md` §14 | disable dual-write for that source. Legacy never stopped. |
| Legacy | — | **never.** Legacy is not modified by Phase 4, so there is nothing to roll back. |

Order is fixed: comparator before dual-write, dual-write before anything else, and nothing
touches legacy. Code rolls back before data; no receipt store is deleted in the same release
as a code change.

**Criteria for declaring the observability work itself failed** — as distinct from finding a
defect in the ingest path:

1. The comparator cannot classify a material share of pairs (`unclassified` > 0.1 % over a
   day). A reconciler that shrugs at one pair in a thousand is not evidence.
2. Conservation does not close on two consecutive runs.
3. Two runs over the same window produce different verdicts with no change on either side.
4. A receipt is found containing a coordinate, a credential or a payload body.

Any of these stops the dual-write stage — not just the comparator — because without a
trustworthy comparison the exit gate in §13.3 of the ingest spec cannot be evaluated at all,
and an unevaluable gate must not be passed by assumption.
